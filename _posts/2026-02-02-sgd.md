No post anterior implementei a regressão linear com **Batch Gradient Descent**: a cada época, o algoritmo varre o dataset inteiro, calcula o erro de todos os exemplos, e dá *um único passo* na direção oposta ao gradiente. Funciona bem, mas tem um problema óbvio, em datasets grandes, varrer tudo só para dar um passo é caro.

Neste post, exploro duas alternativas que  logo na sequência: o **Stochastic Gradient Descent (SGD)** e o **Mini-batch SGD**. Os três algoritmos juntos formam o "capítulo de otimizadores" da biblioteca, e fecham a infraestrutura de treino que vou reutilizar nos modelos seguintes.

## A motivação: muitos passos baratos vs. poucos passos exatos

A intuição central do SGD é uma inversão do BGD. Em vez de calcular o gradiente exato (caro) e dar um passo perfeito, calculamos um gradiente **aproximado e barulhento** usando um único exemplo de treino, e damos um passo imperfeito. Isso parece pior, e em certo sentido é, mas o ganho está no volume: enquanto o BGD dá uma atualização por passada no dataset, o SGD dá $n$ atualizações na mesma passada.

Como as notas de aula do AndrewNG colocam:

> *Whereas batch gradient descent has to scan through the entire training set before taking a single step — a costly operation if n is large — stochastic gradient descent can start making progress right away, and continues to make progress with each example it looks at. Often, stochastic gradient descent gets θ "close" to the minimum much faster than batch gradient descent.*

A contrapartida é que o SGD **não converge no sentido estrito**, os parâmetros oscilam em torno do mínimo de $J(\theta)$. Mas, na prática, qualquer ponto razoavelmente próximo do mínimo já serve, e isso costuma ser alcançado bem antes do BGD terminar uma única passada cara.

## O algoritmo de SGD

Partindo da regra do BGD vista no post anterior:

$$
\theta := \theta + \alpha \sum_{i=1}^{n} \bigl(y^{(i)} - h_\theta(x^{(i)})\bigr) x^{(i)}
$$

O SGD simplesmente **tira o somatório** e usa um único exemplo $j$ por atualização:

$$
\theta := \theta + \alpha \bigl(y^{(j)} - h_\theta(x^{(j)})\bigr) x^{(j)}
$$

Essa equação parece quase a mesma, mas três coisas mudam de forma sutil, e cada uma delas me apareceu como uma decisão na hora de codar.

**Sumiu o `/m`.** No BGD, eu dividia o gradiente acumulado por $m$ para tirar a média da soma. No SGD não há soma para tirar média, o "batch" é de tamanho 1.

**Uma "época" muda de significado.** No BGD, uma época era uma atualização. No SGD, uma época é uma passada completa pelo dataset, com $n$ atualizações. O que era um *for loop* simples vira um loop aninhado.

**O vetor de erro vira escalar.** Como a operação é em um exemplo só, $y^{(j)} - h_\theta(x^{(j)})$ é um número, não um vetor. A vetorização $X^T \vec{e}$ que tornava o BGD elegante se reduz aqui, embora reapareça no mini-batch.

## O detalhe do shuffle

Esse é um ponto que **não existia no BGD** e merece atenção.

Se os dados estiverem ordenados por algum atributo (por classe, por região geográfica, por data), iterar em ordem faz o gradiente puxar $\theta$ consistentemente para um lado durante a primeira metade da época e para o outro lado durante a segunda. Em vez do ruído estocástico bem-comportado que o algoritmo precisa, você ganha um zigue-zague de larga escala que destrói a convergência.

A solução padrão é **embaralhar a ordem dos índices no início de cada época**. Crio um vetor `[0, 1, ..., n-1]`, aplico um `std::shuffle` nele, e itero pelos índices embaralhados. As notas mencionam duas variantes (sortear $j$ uniformemente a cada passo vs. embaralhar e iterar em ordem), e a segunda é a forma idiomática, garante que cada exemplo é visto exatamente uma vez por época.

> O gerador de números aleatórios deve ser criado **fora** do loop de épocas. Recriá-lo a cada época faz com que a sequência de embaralhamentos vire determinística entre execuções, o que pode mascarar bugs ou criar comportamentos estranhos.
{: .prompt-warning }

## Como medir o custo no SGD

Outro detalhe que só aparece agora: no BGD, eu calculava `h_theta = X * theta` para o dataset inteiro a cada época, então imprimir o custo $J(\theta)$ era praticamente de graça — todos os ingredientes já estavam ali. No SGD, cada atualização vê um exemplo só, e o "erro daquele exemplo" é uma medida ruidosa que não representa $J(\theta)$.

Se eu quiser monitorar a convergência, preciso periodicamente, por exemplo, ao fim de cada época, recalcular o custo no dataset inteiro **separadamente** do loop de atualização. Isso custa uma passada extra, mas é barato em comparação com a atualização que eu fiz $n$ vezes naquela época.

## A implementação do SGD

O resumo da função `treinarSGD`:

```cpp
void RegressaoLinear::treinarSGD(const matriz& dadosX, const matriz& respostaY)
{
    this->calcularMinMax(dadosX);
    matriz X_norm = this->normalizar(dadosX);


    matriz X_vies = this->adicionarVies(X_norm);
    int m = X_vies.getLinhas();
    this->pesosTheta = matriz(X_vies.getColunas(), 1);
    this->pesosTheta.preencherAleatorio();


    std::random_device rd;
    std::mt19937 g(rd());
    for(int i = 0; i < this->epocas; i++)
    {
        std::vector<int> indices(m);
        for(int a = 0; a < m; a++) indices[a] = a;

        std::shuffle(indices.begin(), indices.end(), g);

        for(int k = 0; k < m; k++)// loop no dataset
        {
            int j = indices[k];
            matriz linhaX = X_vies.getVector(j);
            matriz linhaY = respostaY.getVector(j);

            matriz h_theta = linhaX * this->pesosTheta; 
            matriz erro = linhaY - h_theta;

            matriz gradiente = linhaX.transposta() * erro;

            double passo = this->taxa_aprendizado; 
            this->pesosTheta = this->pesosTheta + (gradiente * passo);


        }
        matriz h_theta = X_vies * this->pesosTheta; 
        matriz erro = respostaY - h_theta;
        matriz algo  = erro.transposta() * erro;
        if( i % 50 == 0)
        {
            std:: cout << "Epoca: " << i << "  Função Custo(J): " << algo.getValor(0,0)/(2.0*m) << std::endl;
        }




    }
}

```
{: file='RegressaoLinear.cpp' }

A fase de preparação (calcular min/max, normalizar, adicionar viés, inicializar $\theta$) é idêntica à do `treinar` original. A diferença está nos dois loops aninhados: o externo sobre as épocas, o interno sobre os índices embaralhados. Dentro do loop interno, é onde a regra de atualização aparece quase literalmente.

| Fórmula | Código |
|:--------|:-------|
| índice embaralhado $j$ | `indices[k]` |
| $h_\theta(x^{(j)}) = x^{(j)} \theta$ | `linha_j * pesosTheta` |
| $e^{(j)} = y^{(j)} - h_\theta(x^{(j)})$ | `respostaY.getValor(j,0) - h_j` |
| $\theta := \theta + \alpha \cdot e^{(j)} \cdot x^{(j)}$ | `pesosTheta = pesosTheta + linha_j_T * (taxa_aprendizado * e_j)` |

## Mini-batch SGD: o meio-termo

O mini-batch é literalmente uma generalização que **interpola** entre os dois extremos:

- $B = 1$ → SGD puro
- $B = n$ → BGD
- $B$ no meio (tipicamente 32, 64, 128) → mini-batch SGD

A regra de atualização do Algorithm 2 das notas:

$$
\theta := \theta - \frac{\alpha}{B} \sum_{k=1}^{B} \nabla_\theta J^{(j_k)}(\theta)
$$

Repare que o $\frac{1}{B}$ reaparece. No BGD ele era $\frac{1}{n}$, no SGD puro sumiu (porque $B = 1$), e no mini-batch volta — é a **média do gradiente** sobre o lote. Essa volta da média é o que torna o comportamento do otimizador mais previsível.

A justificativa prática para usar mini-batch (e não SGD puro) está nas próprias notas:

> *Computing the gradient of B examples simultaneously for the parameter θ can be faster than computing B gradients separately due to hardware parallelization.*

Em outras palavras: uma multiplicação de matriz de tamanho $B \times (d+1)$ por $(d+1) \times 1$ aproveita SIMD e cache de forma muito melhor que $B$ multiplicações vetor-vetor sequenciais. É por isso que o mini-batch é o padrão em deep learning hoje, mesmo em datasets onde o SGD puro convergiria.

## A implementação do Mini-batch SGD

```cpp
void RegressaoLinear::treinarminiBatchSGD(const matriz& dadosX, const matriz& respostaY, int batch_size)
    {
        this->calcularMinMax(dadosX);
        matriz X_norm = this->normalizar(dadosX);


        matriz X_vies = this->adicionarVies(X_norm);
        int m = X_vies.getLinhas();
        this->pesosTheta = matriz(X_vies.getColunas(), 1);
        this->pesosTheta.preencherAleatorio();


        std::random_device rd;
        std::mt19937 g(rd());
        for(int i = 0; i < this->epocas; i++)
        {
            std::vector<int> indices(m);
            for(int a = 0; a < m; a++) indices[a] = a;

            std::shuffle(indices.begin(), indices.end(), g);



            for(int k = 0; k < m; k = k + batch_size)// loop no dataset
            {

                int tamanho_real = std::min(batch_size, m - k);

                matriz zerada(X_vies.getColunas(), 1);


                for(int b = 0; b < tamanho_real; b++)
                {
                    int j = indices[k + b];
                    matriz linhaX = X_vies.getVector(j);
                    matriz linhaY = respostaY.getVector(j);

                    matriz h_theta = linhaX * this->pesosTheta; 
                    matriz erro = linhaY - h_theta;

                    matriz gradiente = linhaX.transposta() * erro;

                    zerada = zerada + gradiente;

                }
                

                 double passo = this->taxa_aprendizado / tamanho_real; // tirar a média do gradiente
                this->pesosTheta = this->pesosTheta + (zerada * passo);
            }
            matriz h_theta = X_vies * this->pesosTheta; 
            matriz erro = respostaY - h_theta;
            matriz algo  = erro.transposta() * erro;
            if( i % 50 == 0)
            {
                std:: cout << "Epoca: " << i << "  Função Custo(J): " << algo.getValor(0,0)/(2.0*m) << std::endl;
            }




        }
    }
```
{: file='RegressaoLinear.cpp' }

A estrutura é quase idêntica à do SGD. Duas mudanças principais:

1. O loop interno avança de $B$ em $B$ em vez de 1 em 1.
2. Dentro de cada batch, eu monto uma submatriz $X_{batch}$ ($B \times (d+1)$) e o respectivo vetor $\vec{y}_{batch}$, e aí a vetorização do BGD volta inteira:

$$
\vec{e}_{batch} = \vec{y}_{batch} - X_{batch}\theta, \qquad \nabla = X_{batch}^T \vec{e}_{batch}, \qquad \theta := \theta + \frac{\alpha}{B} \nabla
$$

| Fórmula | Código |
|:--------|:-------|
| $X_{batch}\theta$ | `X_batch * pesosTheta` |
| $\vec{y}_{batch} - X_{batch}\theta$ | `y_batch - h_batch` |
| $X_{batch}^T \vec{e}_{batch}$ | `X_batch.transposta() * erro_batch` |
| $\theta + \frac{\alpha}{B} \nabla$ | `pesosTheta + (gradiente * (taxa_aprendizado/tamanho_real))` |

> **Cuidado com o último batch.** Se $n$ não for divisível por $B$, o último mini-batch da época vai ter menos de $B$ exemplos. No meu caso, com 399 amostras e $B = 32$, são 12 batches de 32 e um último batch de 15. A divisão precisa ser pelo **tamanho real** do batch, não por $B$ fixo, ou o gradiente final fica deformado.
{: .prompt-warning }

## A descoberta empírica: taxa de aprendizado escala com B

Esse foi, talvez, o resultado mais interessante da implementação — porque saiu de rodar o código e ver dar errado, não da teoria.

Rodei os três cenários com a mesma taxa de aprendizado $\alpha = 0.001$ e 500 épocas:

| Cenário | $B$ | Custo final |
|:--------|:---:|:-----------:|
| SGD puro | 1   | 6.05 |
| Mini-batch | 32  | 13.98 |
| BGD (via mini-batch) | 399 | 70.69 |

O caso $B = 1$ convergiu — está praticamente em cima do ótimo (~5.85, validado contra `LinearRegression` do scikit-learn). Os outros dois mal se mexeram. Por quê?

Porque no meu código `passo = α / tamanho_real`. Olha o que acontece com o passo efetivo:

| $B$ | Passo efetivo |
|:---:|:-------------:|
| 1   | $0{,}001$ |
| 32  | $0{,}00003$ |
| 399 | $0{,}0000025$ |

Com $B = 399$, o passo é 400 vezes menor que com $B = 1$. Não tem como convergir em 500 épocas — é como rodar o BGD com taxa minúscula. Não era bug, era a fórmula fazendo o que deveria.

A correção foi escalar $\alpha$ proporcionalmente ao batch:

| $B$ | $\alpha$ ajustada | Custo final |
|:---:|:-----------------:|:-----------:|
| 1   | $0{,}001$ | $\approx 6{,}0$ |
| 32  | $0{,}03$  | $\approx 6{,}0$ |
| 399 | $0{,}1$   | $\approx 6{,}0$ |

Esse comportamento tem nome na literatura: **linear scaling rule**. A regra prática que sai dela é: ao aumentar o tamanho do batch, aumente a taxa de aprendizado proporcionalmente. É uma das pedras angulares do treinamento de redes neurais grandes hoje, e descobri ela acidentalmente implementando um otimizador para regressão linear.

## Dois pontos que me deixaram curioso

No mesmo espírito do post anterior, deixo aqui duas perguntas que apareceram no caminho.

### Por que o SGD funciona se cada gradiente é "errado"?

Cada gradiente do SGD é calculado com base em **um único exemplo**, então ele não aponta para a direção que minimiza $J(\theta)$ globalmente — aponta para a direção que minimiza o erro **daquele exemplo específico**. Por que essa sequência de chutes individuais converge?

A resposta vem de pensar no gradiente estocástico como um **estimador não-viesado** do gradiente real. Para um exemplo $j$ sorteado uniformemente:

$$
\mathbb{E}_j\left[\nabla_\theta J^{(j)}(\theta)\right] = \frac{1}{n}\sum_{i=1}^{n} \nabla_\theta J^{(i)}(\theta) = \nabla_\theta J(\theta)
$$

Em palavras: na **média**, o gradiente estocástico é o gradiente real. As atualizações individuais são ruidosas, mas o ruído tem média zero. Ao longo de muitas atualizações, esses ruídos se cancelam e o efeito líquido é caminhar na direção do gradiente verdadeiro.

A imagem que ajudou a fixar isso na minha cabeça: imagine que você está descendo uma colina com os olhos vendados. O BGD é alguém que para a cada passo, mede a inclinação do terreno em todos os lados, e dá um passo perfeito morro abaixo. O SGD é alguém que sente o chão com o pé, dá um passo na direção que parece descer ali naquele instante, e segue em frente. O segundo dá passos errados o tempo todo, mas como dá muitos mais, chega antes na maioria das vezes.

### Por que `α/B` precisa ser ajustada — não é "automática"?

Essa é a outra metade da intuição da seção anterior. A pergunta natural é: já que estou dividindo o gradiente acumulado por $B$ (tirando a média), o tamanho do batch não deveria ser **invisível** para o algoritmo? A magnitude do gradiente médio não cresce com $B$.

E é exatamente isso o problema. O gradiente médio tem **magnitude** parecida para qualquer $B$ — o que muda com $B$ é a **qualidade do estimador**. Gradientes calculados com $B$ grande são menos ruidosos, mais próximos do gradiente verdadeiro. Gradientes com $B$ pequeno são mais ruidosos.

E aqui está a conexão: quando o gradiente é confiável (B grande), você pode dar **passos maiores** com segurança — afinal, o passo aponta numa direção precisa. Quando o gradiente é ruidoso (B pequeno), passos grandes te jogam em direções erradas, então você precisa de passos menores para o ruído se cancelar.

Daí a linear scaling rule: B maior → gradiente mais confiável → posso aumentar $\alpha$. Não é uma quebra do algoritmo, é o algoritmo te oferecendo um trade-off entre custo computacional e tamanho de passo.

> Em produção, essa relação é mais sutil — existem técnicas de *warmup* da taxa de aprendizado, *learning rate schedulers*, e correções para batches muito grandes onde a regra linear quebra. Mas para os tamanhos de batch que aparecem na prática (16 a 1024), a regra linear é uma ótima primeira aproximação.

## Fechamento

Com isso, fecho o capítulo de otimizadores da biblioteca. Tenho agora três variantes da mesma ideia:

| Otimizador | Atualizações por época | Custo por atualização | Quando usar |
|:-----------|:----------------------:|:---------------------:|:------------|
| **BGD**    | 1                      | $O(n \cdot d)$        | Datasets pequenos, debug |
| **SGD**    | $n$                    | $O(d)$                | Datasets enormes |
| **Mini-batch** | $n/B$              | $O(B \cdot d)$        | Praticamente sempre |

E levei comigo duas lições que valem mais que o código em si: a primeira, que o SGD funciona porque ruído com média zero não atrapalha — desde que você esteja disposto a dar muitos passos; a segunda, que a taxa de aprendizado e o tamanho do batch são acoplados, e tratar um sem ajustar o outro é receita de modelo que "não converge" sem que haja bug nenhum.

A próxima parada é onde tudo isso vira ferramenta de verdade: redes neurais. Toda a infraestrutura de treino agora está pronta para um modelo mais expressivo que uma combinação linear das features — e o mini-batch SGD que acabei de implementar é, literalmente, o otimizador padrão de praticamente todos os modelos de deep learning treinados hoje.
